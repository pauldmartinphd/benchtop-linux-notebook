## Findings

- Synchronous discard on installed systems is systemd issue 38829: systemd-repart's `--generate-fstab` puts `discard` on every entry except the EFI partition, and on Btrfs that is synchronous discard. The issue suggests adding `discard=async` to `MountPoint=`; Btrfs applies discard options in order (checked in the kernel source, 6.18 and mainline).
- The pause during the copy: with `--empty=force`, systemd-repart discards the whole disk, skips its per-partition discards, and still has mkfs.btrfs discard the new encrypted root. systemd 260's "discard only once" (PR 40579) counts only the per-partition discards. From systemd's source; the kernel stacks during the pause were not captured.
- Aeon uses the same tik (1.5.1), the same `50-root.conf` (systemd-repart-branding-Aeon) and the same systemd, so its installs probably get the same fstab. No Aeon report found; not checked on an Aeon system.
- SELinux: neither tik nor Aeon relabels after the copy. openSUSE's selinux-autorelabel, which microos-tools requires, relabels at the next boot when `/etc/selinux/.autorelabel` exists, in the initrd for the root snapshot, `/etc` and `/var`; that replaces a TCBL relabel module.
- Racket and amdgpu_top: Tumbleweed has only the full racket package, and amdgpu_top's graphical interface is compiled into the same program. Both stay installed; their graphical launchers are left out of the app grid by the rpm macro that already leaves out the htop, nvtop and atop launchers.

- Builds: the Build Service had not synced any push since the morning of October 25 (tc-benchtop-settings at `e7d7d0b`; patterns and image had nothing new until today, apart from the history rewrite). So rasdaemon, enabled in `0d39d7c`, was in no package or image. The cause: the GitHub token behind the Build Service workflow token, a classic token with `repo:status`, expired on October 24. The workflow files and the pre-push hook were checked and work.
